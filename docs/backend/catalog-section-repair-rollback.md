# Rollback — catalog section repair (GR-02 / REQ-004)

How to undo `supabase/migrations/20261001000019_catalog_section_repair.sql`.

The repair adds section tags, and raises `can_be_primary`, on the 28 exercises named in
`docs/process/generation-reliability/section-mapping-ledger.json`. It inserts and removes no row
and touches no other column, so the rollback is small: put `sections` and `can_be_primary` on
those 28 rows back to what the pre-change capture holds.

- **Pre-change capture:** `docs/backend/snapshot/2026-09-18T162821Z/catalog/exercise_definitions.csv`
- **Rollback script:** `docs/backend/rollback/catalog-section-repair.sql`

The script is generated by `npm run gr:repair` from the ledger (which rows) and the capture (which
values). It is not hand-written and must not be hand-edited:
`src/test/generation-reliability/catalog-repair-migration.test.ts` fails if it stops matching either,
and proves that applying it to the repaired catalog gives back the capture. It is not a migration
and no command applies it.

For the cutover-wide rollback, which restores the whole project from the off-machine backup, see
`docs/backend/rollback.md`. This procedure is the narrow one and needs no backup.

## When to use it

When the repaired sections have to be withdrawn: the three sections are to be empty again and
Minimal main work is to be un-tagged. That is a product decision, and it reopens the states the
repair closed — `skill_power`, `carries` and `stability_balance` return no candidate at any tier.
Decide what happens to profiles that have those sections switched on before running it.

It is not the fix for one wrong row. A wrong row is corrected in the ledger, with evidence, and
`npm run seed` and `npm run gr:repair` regenerate from it.

## Procedure

The database and the repository are rolled back together. If only the database is, the next seed
apply or `supabase db reset` re-applies the repair, because the committed seed carries it.

1. **Repository first.** Revert the commit that applied the ledger, on a branch, through a pull
   request. That takes away the migration file, puts `supabase/seed/010_exercise_definitions.sql`
   and `docs/process/generation-reliability/legal-state-matrix.json` back to the unrepaired catalog,
   and restores the seed's reviewed expectations. Confirm on the branch:

   ```sh
   npm run seed -- --check
   npm run gr:matrix -- --check
   ```

   Keep a copy of `docs/backend/rollback/catalog-section-repair.sql` from before the revert; the
   revert removes it.

2. **Record what is there.** Against the target database, before changing anything:

   ```sql
   select id, sections, can_be_primary
   from public.exercise_definitions
   where sections && array['skill_power', 'carries', 'stability_balance']::public.section_type[]
      or can_be_primary
   order by id;
   ```

   Save the output with the change record. It is what a re-apply would be checked against.

3. **Run the rollback script** through the same protected path a migration takes — never from an
   agent session, and never against the hosted project without the owner's explicit go-ahead:

   ```sh
   psql "$SUPABASE_DB_URL" -v ON_ERROR_STOP=1 -f catalog-section-repair.sql
   ```

   It is one `update` in a transaction, guarded by `is distinct from`: it reports `UPDATE 28` on a
   repaired catalog and `UPDATE 0` if run again.

4. **Verify.** All three must hold:

   ```sql
   -- 0: the three sections are empty again.
   select count(*) from public.exercise_definitions
   where sections && array['skill_power', 'carries', 'stability_balance']::public.section_type[];

   -- 25: primary_lift is back to its captured membership.
   select count(*) from public.exercise_definitions where 'primary_lift' = any (sections);

   -- 140: no row was added or removed.
   select count(*) from public.exercise_definitions;
   ```

5. **Mark the migration reverted**, so the migration history matches the reverted repository:

   ```sh
   supabase migration repair --status reverted 20261001000019
   ```

## What it does not undo

- Workouts already generated. A saved session that used a repaired section keeps its exercises; the
  rollback changes what retrieval offers next, not history.
- Profiles with `skill_power`, `carries` or `stability_balance` enabled. They are left as they are
  and return to failing before composition.
- Anything outside the 28 ledger rows. If a row's tags were changed by something else after the
  repair, the script overwrites that change with the captured value; step 2's output is how that
  would be noticed.

## Re-applying

Undo the revert and apply the migration again. It is idempotent: it appends only the tags a row is
missing, so it is safe on a catalog that is repaired, unrepaired, or partly either.
