## Decisions and assumptions

- Any failing row refuses, not only rows that block the proposed goal. REQ-010 defines a viable
  configuration as one where every goal and focus Generate offers resolves, active recovery included,
  and the commit uses that definition unchanged. A section only recovery asks for gets a sentence
  that does not offer "turn it off".
- The refusal travels as the exception's DETAIL rather than a second `generation_viability` call from
  the client, so the rows named are the ones the transaction judged.
- `CLR11` is a custom SQLSTATE. PostgREST's documented default for an unrecognised code is HTTP 400;
  the client keys on `pgCode`, not on the status, so a different status would still be recognised.
- The refusal stays on the confirm step rather than jumping to the step that owns the named choice;
  Back reaches it with every value intact.

Decisions and assumptions:

- **A trigger, not an RPC Settings is expected to call.** "Enforced server-side" is then true of the
  rows: a direct PATCH meets the same refusal, and the raise aborts the statement so nothing is
  stored. Settings needed no change — its optimistic write already rolls back on any failed save and
  shows the error's message in the existing toast.
- **Only an introduced failure is refused.** The configuration is evaluated as it stood and as it
  would stand; a (location, section, class) that was already failing does not refuse the write,
  unless it now blocks the saved Goal and did not block the previous one. Otherwise an athlete saved
  before the guard — or hit by a catalog gap — could never edit anything, including the fix. This
  reads REQ-012's "changing … to a combination that cannot generate" as about the change.
- **Onboarding and location writes are not guarded here.** The profile trigger skips a profile that
  is not onboarded; the constraint trigger skips when `onboarded_at = now()`, i.e. inside
  `complete_onboarding`'s own transaction. A re-run of onboarding by an already-onboarded user is
  guarded on its profile update. No trigger on `locations` / `location_equipment`: an equipment
  change that strands the saved preferences is the location task's.
- DELETE of a constraint and a note-only update are not guarded: neither can narrow eligibility.
  Session-scoped rows are not saved settings and are not read.
- Pattern and section names in the sentence are the enum value with underscores as spaces, as
  TASK-012 chose and for the same reason (`errors.ts` is imported by the edge functions).
- A catalog gap names no place; the other classes name every place they fail at.
