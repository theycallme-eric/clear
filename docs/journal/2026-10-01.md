# 2026-10-01 — provider failure made actionable

VIBE-D merged through the normal protected path, but both post-merge checks stayed honestly red at
the same boundary: 102 trusted-backend checks passed before live composition returned 502, and the
exact production deployment's new-user journey reached the same response. The Supabase function
log shows context resolution and prompt assembly succeeded before both provider attempts failed as
`generation.upstream` in well under two seconds.

The runtime had enough information to distinguish the provider response internally, but the
structured warning logged only the broad failure code. That made an invalid key, insufficient
credit, a malformed request, a quota limit, and provider overload operationally indistinguishable.
`claude.ts` now includes its already-sanitized attempt detail in the warning. That detail is only an
HTTP status, exception name, schema path, or validator explanation; provider bodies, prompts,
headers, and keys are never copied into it. Tests prove a simulated 529 is visible on both attempts
while its response body and API key remain absent.

The live secret inventory supplied the other concrete clue: `ANTHROPIC_API_KEY` exists but its
deployed value was last updated on 21 January 2026. Paying or creating a key in a different
Anthropic workspace cannot repair that old stored value. Once this safe logging repair is deployed,
one bounded live call will name the exact provider status before any secret is replaced; the
replacement, if required, must be made directly in Supabase and never pasted into chat or committed.

This is a reusable automation lesson: a provider gate needs three separate proofs before dependent
work is called runnable—secret name present, credential updated for the intended workspace, and a
minimal capability probe that records a non-sensitive upstream status. Presence alone is not
capability.
