### Decisions worth recording

**Why the day is computed on the client.** Postgres could bucket `completed_at` into days, but only
the browser knows which zone to bucket it into and there is no `profiles.time_zone` column. Putting
the bucketing in SQL would have meant either passing a zone into every query or storing one; the
derivation therefore receives instants and resolves the zone once, which is also what makes the
11pm/1am case a test rather than a hope.

**"No stored streak" is asserted against the whole schema.** A test reading only the new migration
cannot prove a negative about the schema, so `streak-migration.test.ts` uses the generator's SQL
reader over every migration: the only column matching `/streak/i` is
`workout_sessions.counts_for_streak`, and the six columns the old app kept are asserted absent by
name. A future migration that reintroduces one fails this test wherever it is added.

### Failures and corrections

- `npm run gen:types` could not be run in this environment (the harness permits only the
  controller's verification commands). The generated types were instead updated by hand to exactly
  what the generator produces, and `src/test/generated-types.test.ts` — which compares
  `src/data/database.types.ts` byte for byte against a fresh `build()` — is what confirms the result
  is the generator's output rather than a plausible imitation. It passes. The migration list in that
  test was updated for the new file.
- One test failed on first run: the policy was never asked about a day earlier than the oldest row
  supplied, because the walk stops where the data stops. That is the intended behaviour — guessing
  past the last row is how a derived number starts being wrong — so the test was corrected to supply
  an older session rather than the walk being changed.
