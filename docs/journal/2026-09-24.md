### Intended outcome

### What changed

  returning `session_id, completed_at, counts_for_streak` for completed sessions, newest first, plus
  the partial index `(user_id, completed_at desc) where completed_at is not null`. The function
  counts nothing, buckets no days and applies `counts_for_streak` to nothing; it filters on the
  lifecycle only.
- `src/state/streak.ts` — `deriveStreak`, pure. One `Intl.DateTimeFormat` built per derivation from
  the caller's zone, a backwards walk over calendar days, and `StreakPolicy` as the named extension
  point (`countsForStreak`, `bridgesDay`) that HOME-02 will supply pause states and rest-day
  allowances through.
- `src/data/streak.ts` — the read: zone resolved once when the client is created, one RPC in the
  ordinary case, and a cursor that asks for the page before only when the derived run reaches the
  oldest row already held.
- `src/state/schemas.ts` — `streakSessionRowSchema` / `streakSessionPageSchema` (CORE-03: the data
  module parses, and owns no zod of its own).
- Tests: `src/state/streak.test.ts` (28 cases — zones, DST, month/year boundaries, two sessions in
  one day, abandoned and deleted rows, the policy hook), `src/data/streak.test.ts` (the RPC, the

- `src/test/factories.ts` gained `makeSessionRow`; `src/test/session-double.ts` answers
  `streak_sessions` with the function's own rules; `PROJECT_MAP.md` and both boundary READMEs record
  the flow.

### Decisions worth recording

**Why the day is computed on the client.** Postgres could bucket `completed_at` into days, but only
the browser knows which zone to bucket it into and there is no `profiles.time_zone` column. Putting
the bucketing in SQL would have meant either passing a zone into every query or storing one; the
derivation therefore receives instants and resolves the zone once, which is also what makes the
11pm/1am case a test rather than a hope.

**"No stored streak" is asserted against the whole schema.** A test reading only the new migration
cannot prove a negative about the schema, so `streak-migration.test.ts` uses the generator's SQL
reader over every migration: the only column matching `/streak/i` is
`workout_sessions.counts_for_streak`, and the six columns the old app kept are asserted absent by
name. A future migration that reintroduces one fails this test wherever it is added.

### Failures and corrections

- `npm run gen:types` could not be run in this environment (the harness permits only the
  controller's verification commands). The generated types were instead updated by hand to exactly
  what the generator produces, and `src/test/generated-types.test.ts` — which compares
  `src/data/database.types.ts` byte for byte against a fresh `build()` — is what confirms the result
  is the generator's output rather than a plausible imitation. It passes. The migration list in that
  test was updated for the new file.
- One test failed on first run: the policy was never asked about a day earlier than the oldest row
  supplied, because the walk stops where the data stops. That is the intended behaviour — guessing
  past the last row is how a derived number starts being wrong — so the test was corrected to supply
  an older session rather than the walk being changed.

## EXE-01 — block completion centralised (REQ-045, issue #92, TASK-045B)

Branch `agent-runner/task-045b-a1-5aefbf29`, worked in an isolated worktree. Nothing was pushed, no
pull request was opened, and no external service was changed: every result below is local.

### Intended outcome

The slice of EXE-01 that is about *one* path: every structure type completes through the shell, the
structure-specific outcome fields and the 1–10 perceived effort are written once to `block_results`,
and no renderer can grow a competing persistence path.

### What was already true, and what was not

TASK-045 landed the shell with block completion inside it: `block-completion.ts` (the outcome
vocabulary and the row mapping), `block-effort.tsx` (the one effort dialog), the `block_results`
writer in `data/workout.ts`, and the pending/record state inside `WorkoutShell`. So the *behaviour*
of criterion 1 and 2 existed. Three things did not:

- nothing enforced criterion 3. The completion path was code inside a screen, and a renderer that
  wrote its own row would have passed every test in the suite;
- no structure type had a renderer, and the seam had never been exercised by one — every test
  completed a block with an empty outcome, so "the renderers supply the structure-specific fields"
  was asserted nowhere;
- the effort range was mirrored in `isPerceivedEffort` but never applied: the writer sent whatever
  number it was handed, and a value outside 1–10 would have come back as a PostgREST 400.

### What changed

- `src/state/block-completion-provider.tsx` (new) — the completion path as a module: the effort
  question, the `block_results` write, the record of what this session has already written, and the
  refusal of a second completion for the same block. Failures are handed up rather than rendered, so
  the shell keeps one error surface. `Workout.tsx` mounts it and lost ~110 lines.
- `src/ui/block-renderers.tsx` (new) — `BLOCK_RENDERERS`, total over `structure_type`, plus the
  default `BlockPanel` moved out of `Workout.tsx` and rewritten to take completion from
  `useBlockCompletion()` rather than from props. A renderer now receives no client and no callback,
  which is the property the ownership test asserts. `BlockSlot` dispatches with `createElement` —
  JSX over a looked-up local is what `react-hooks/static-components` refuses, and it is right to.
- `src/data/workout.ts` — `record` refuses an effort outside 1–10 with `VALIDATION_OUT_OF_RANGE`
  before anything is sent. One path, so one check covers every structure type.
- `src/dev/gallery-registry.test.tsx` — `BlockPanel` and `BlockSlot` recorded as non-specimens for
  the same reason the other EXE-01 shell parts are: they read live session state.
- `PROJECT_MAP.md` — the completion flow rewritten around the provider, the registry and the guard.

### Tests written this session (40 new, four files)

- `src/state/block-completion-provider.test.tsx` — the criterion that had no test: a *renderer*
  supplying an outcome. Six structure types, each with the fields DATA_MODEL §8 says it observes,
  each landing as one completion with the effort the shell captured; a table asserted equal to the
  `structure_type` enum, so a seventh type cannot be added without one. Plus: effort asked once per
  block, a second completion of a written block refused, a completion naming a block outside the
  session ignored, a failed write handed up with the block still completable, a dismissed question

- `src/ui/block-renderers.test.tsx` — the map is total, dispatch matches it, and every structure
  type completes through `completeBlock` with an empty outcome rather than a fabricated zero.
- `src/test/block-completion-ownership.test.ts` — the structural guard, in the repository's existing
  idiom: exactly one file names the table, calls the row mapping, calls `record`, mounts the effort
  dialog and provides the seam; no file in `src/ui/` imports a transport; every file that calls
  `completeBlock` takes it from `useBlockCompletion()`. It is self-checking — it asserts it found
  the sources it is scanning, so a broken walk fails rather than passes.
- `src/data/workout.test.ts` — the writer at the wire: the mapped row, the live token per call, the
