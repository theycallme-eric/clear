# Production visual follow-up — missing CLEAR font faces

The first owner visual check after TASK-072 showed the Sign In screen rendering generic system
fonts instead of Rajdhani, Oxanium, and Space Grotesk. This was a platform-wide typography defect,
not a one-screen override: the role tokens named the right families, but no loaded stylesheet
provided their font faces.

TASK-025's own 2026-09-20 journal entry had disclosed the cause precisely: its worker could not
reach the npm registry, removed the Google CDN path, and shipped fallback stacks while stating
that the self-hosted half was **not delivered**. The generated GitHub issue reduced the detailed
requirement to one acceptance checkbox—"No Google Fonts requests in production build"—so CI
proved only that the CDN was absent. It never proved that replacement faces existed or rendered.
The task was then merged, closed, and counted complete despite the worker's explicit incomplete
status. TASK-072's production closeout checked function, data, auth, deployment, and HTTP health,
but had no visual/typeface assertion, so it did not catch the earlier design defect.

The repair installs the three approved Fontsource packages, imports exactly Rajdhani 500/600/700,
Oxanium 400/500/600/700, and Space Grotesk 400/500/700 in the app-owned skin, and preloads the
three above-the-fold faces. Source tests now enumerate every required family/weight and inspect
the package rules for local woff2 delivery and `font-display: swap`. A browser E2E assertion loads
the three role faces, checks the heading/body computed families, and rejects font responses from
any origin other than the app.

The reusable workflow lesson is not "add a font test to Clear." Requirements Builder must preserve
every acceptance bullet that distinguishes presence from absence, and Agent Runner must treat an
explicit `incomplete`, `not delivered`, or unmet-acceptance declaration in worker evidence as a
terminal non-success even when the narrower automated commands pass. Project Control should show
that conflict directly instead of displaying the task as complete. Release verification also needs
a rendered design-system smoke lane (fonts plus representative visual baselines), because an HTTP
200, axe scan, and behavioral test can all pass while the product identity is visibly wrong.
