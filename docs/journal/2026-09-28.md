# Production visual follow-up — missing CLEAR font faces

The first owner visual check after TASK-072 showed the Sign In screen rendering generic system
fonts instead of Rajdhani, Oxanium, and Space Grotesk. This was a platform-wide typography defect,
not a one-screen override: the role tokens named the right families, but no loaded stylesheet
provided their font faces.

TASK-025's own 2026-09-20 journal entry had disclosed the cause precisely: its worker could not
reach the npm registry, removed the Google CDN path, and shipped fallback stacks while stating
that the self-hosted half was **not delivered**. The generated GitHub issue reduced the detailed
requirement to one acceptance checkbox—"No Google Fonts requests in production build"—so CI
proved only that the CDN was absent. It never proved that replacement faces existed or rendered.
The task was then merged, closed, and counted complete despite the worker's explicit incomplete
status. TASK-072's production closeout checked function, data, auth, deployment, and HTTP health,
but had no visual/typeface assertion, so it did not catch the earlier design defect.

The repair installs the three approved Fontsource packages, imports exactly Rajdhani 500/600/700,
Oxanium 400/500/600/700, and Space Grotesk 400/500/700 in the app-owned skin, and preloads the
three above-the-fold faces. Source tests now enumerate every required family/weight and inspect
the package rules for local woff2 delivery and `font-display: swap`. A browser E2E assertion loads
the three role faces, checks the heading/body computed families, and rejects font responses from
any origin other than the app.

The reusable workflow lesson is not "add a font test to Clear." Requirements Builder must preserve
every acceptance bullet that distinguishes presence from absence, and Agent Runner must treat an
explicit `incomplete`, `not delivered`, or unmet-acceptance declaration in worker evidence as a
terminal non-success even when the narrower automated commands pass. Project Control should show
that conflict directly instead of displaying the task as complete. Release verification also needs
a rendered design-system smoke lane (fonts plus representative visual baselines), because an HTTP
200, axe scan, and behavioral test can all pass while the product identity is visibly wrong.

## UAT follow-up — auth entry and mobile atmosphere

The first owner walkthrough then exposed a second false-completion path at the public entry. The
passwordless backend was capable of creating users (`create_user: true`), but the UI exposed only a
Sign in action. The older product and its auth wireframe had made account creation explicit; the
rebuild's generic OTP acceptance criterion proved transport and typed errors while losing that
user-visible affordance. A backend capability is not a complete flow if a visitor cannot discover
it from the interface.

The same walkthrough showed that the full atmosphere looked like a flat scanline background on a
390×844 phone. This was a geometry defect, not missing markup: the exported blobs derived their
height from viewport width but used large negative vertical percentages based on viewport height.
On a portrait screen the orange layer had only a narrow edge inside the viewport and the blue layer
was entirely below it. DOM-presence assertions could not detect that visual absence.

Issue #181 restores an entry card with explicit Sign in and Create account actions. Both retain the
single passwordless OTP backend; the create-account path carries a durable query-string intent and
uses truthful account-creation heading and copy without duplicating authentication logic. An
app-owned portrait media query keeps the existing role colors and intensity tokens while moving all
three blobs meaningfully into view. Unit coverage now proves both user intents, while browser
coverage proves the card, the durable create-account route, and a minimum visible fraction for each
atmosphere layer on both configured viewports. Future requirements must preserve explicit entry
affordances from the source product, and rendered visual acceptance must measure visibility rather
than infer it from mounted elements.

## UAT follow-up — quiet auth atmosphere still read as absent

black scanline field. Issue #181 had corrected portrait geometry and proved that each colored blob

root atmosphere layer. That context raises only the auth presentation to 26% blob opacity under a

Browser coverage now proves the auth context, its computed intensity contract, and meaningful
viewport intersection; the release check still includes a captured phone render because computed
CSS cannot, by itself, prove what a person sees.

new-user email OTP signup. Issue #185 versions the intended hosted template, adds a static contract
test and read-only live drift verifier, narrows the E2E claim, and splits PC-3a into API verification
and real inbox acceptance. PC-3a2 remains open until the owner requests a new message and completes
