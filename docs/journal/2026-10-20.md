**Observed cause (measured, not inferred).** In every row: the `.clr-check` wrapper is 300px wide (x=50..350; the `clr-stack` fieldset stretches it). The 20px drawn box is at x=50..70. Those spans are aria-hidden siblings of the input and the label, not inside the `<label>`, so a press there reaches no control. The input's hit area covers neither the box nor, for most labels, the label text (labels span x=78..~180).

## TASK-029 (#464) — null-safe block-completion effort (REQ-016)

Intended outcome: the block-completion type, insert mapping, `block_results` writer and completion

`agent-runner/task-029-a1-1de841e3`. Nothing was pushed and no PR was opened; the controller owns
delivery.

`blockResultRowSchema.perceived_effort` plus the generated `Insert` type are already nullable.
`src/state/schemas.ts`, the SQL and the generation schema and prompt were not touched.

Local changes:

- `BlockCompletion.perceivedEffort` is now `number | null` and optional. `blockResultInsert`
  writes `null` when it is absent, using the same `recorded()` coalesce as the outcome columns, so
  an observed `0` stays distinct from "not recorded".
- The writer range-checks effort only when one is supplied. Values like 0, 11, 6.5 and NaN are
  still refused before anything is sent.
- The provider now has one `write` path shared by the dialog and a new direct save,
  `completeBlock(id, outcome, { perceivedEffort })`, which TASK-022 will use. A ref-held in-flight
  set means a repeated call cannot write twice. Already-recorded and unknown blocks are still
  refused, a failed write is still handed to `onFailure` and leaves the block completable, and the
  existing dialog flow is unchanged.
- Test double `blockResultRow` coalesces effort to null.
- Tests added in `block-completion.test.ts`, `workout.test.ts`, `block-completion-provider.test.tsx`
  and `schemas.test.ts`.
