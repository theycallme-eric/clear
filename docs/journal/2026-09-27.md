## Verification checkpoint and the integration requirement that was missing

The live browser harness then exposed two harness assumptions rather than product failures:
Supabase is configured for an eight-digit email code while the test required exactly six, and a
hashed email token is verified as `type: email` rather than `type: magiclink`. The harness now
accepts the project-configured numeric length and uses the current token-hash contract. The full
authenticated OTP pair, all six D6 reconstruction checks, and the 87-case Standing RLS matrix pass
against the reused project. RLS fixtures now seed every personal table with positive-control rows;
their denial cases use valid foreign keys and uniqueness values so a green denial is actually RLS,
not an earlier constraint error. Cleanup confirmed the test namespace empty.

That verification also found the important product gap: `generate-workout/index.ts` was still the
typed refusing stub from GEN-01. Retrieval, prompt assembly, Claude transport, validation,
hydration, and acceptance had each been implemented and unit-tested by separate DAG nodes, but no
node owned mounting them into the entry point. A second seam had the same cause: Generate collected
today's goal, while the wire contract omitted it and candidate retrieval used the profile's stored
default. A user choosing Strength could therefore have received candidates for another goal even
after the function was mounted.

The repair is deliberately an integration slice, not a second generation system:

- `generationRequestSchema` now carries today's chosen goal and caller-local date.
- Migration `20260927000018_generation_goal_scope.sql` adds a goal-scoped candidate RPC while
  leaving the original RPC intact for existing session-swap callers.
- `_shared/generate.ts` connects the existing candidate, constraints, recent-focus, anchor,
  prompt, model, validation, hydration, duration, and acceptance modules under the authenticated
  caller's RLS context.
- The success envelope carries `SessionAcceptance`, so Home and Generate hand the exact effective
  request to Review. Review remains the only place a new composition is persisted: pressing Start
  performs the existing one-transaction `persist_session` call; Regenerate discards no rows.
- `generation-integration.test.ts` now proves the seam directly and proves a failed context read
  never calls the composer.

This is also recorded as a Requirements Builder use case outside the Clear repository: a terminal
task should not be the first node that discovers independently completed pipeline parts were never
integrated. Future graphs need an explicit, dependency-aware integration checkpoint before live
cutover, with resumable sub-checkpoints for backup, migration, provider deployment, external
configuration, live verification, and retirement. Approval of an exact task covers its normal
reversible implementation, diagnosis, retry, recovery, reconciliation, and verification; changed
product intent, broader credentials, unrelated resources, and unreviewed destructive effects do
not inherit that approval.
