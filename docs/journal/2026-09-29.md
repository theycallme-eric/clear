## TASK-015 (#203) — the density directive reaches generation

Branch `agent-runner/task-015-a1-39d538ea`. Intended outcome: the `ready` / `hold` / `backing_off`
directive over the last three conditioning sections at intensity 5 or above is computed in code
and carried to the generation prompt, with no directive when fewer than three sections qualify.

- `src/state/conditioning.ts`: `conditioningDirective` now returns `null` when the density window
  holds fewer than `TREND_WINDOW` (3) qualifying sections. Before this it returned `hold` with a
  "only N sections" reason, which the task rules out as a guessed directive. Added
  `conditioningDirectiveOf(rows)` for `conditioning_history(...)` rows.
- `supabase/functions/_shared/generate.ts`: `GenerationDatabase.conditioning(userId)` reads
  `conditioning_history` as the caller (the function's default 60-row window) and parses it with
  `conditioningHistorySchema`. `performGeneration` computes the directive before composing and
  passes its trend into `buildTrainingHistory`. A failed read logs a warning and results in no
  directive; it does not fail the workout.
- `training-history.ts`: `conditioningTrend` is `ConditioningTrend | null` and defaults to `null`,
  not `'hold'`. `prompt.ts` omits the `CONDITIONING TREND:` line when it is null. The system
  prompt text is unchanged, so there is no prompt version bump. Side effect: the swap prompt no
  longer prints `CONDITIONING TREND: hold`, because it never had a directive.
- Interpretation to review: "the generation request" is read as the model request the server
  composes. The trend is not added to the client `generationRequestSchema` payload. Deriving it on
  the server keeps it a read of stored history, not a value the client supplies, and avoids
  omitting it because the client-side query was still loading at submit.
- Tests: `conditioning.test.ts` has a rewritten directive describe block (8 cases): all three
  values, the boundary at 2 vs 3 sections, and the boundary at intensity 4 vs 5.
  `generation-training-history.test.ts` has a new describe block (7 cases) that runs
  `performGeneration` with fixture history and checks the composed user message.
