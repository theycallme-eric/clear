## ENV-03 — Vercel deploy pipeline (issue #3)

**Branch:** `agent-runner/task-003-a1-aabb4b39` · **Intended outcome:** production deploys on
`main`, a preview per pull request, SPA rewrites so a deep link survives a refresh, and the
required environment variables documented in `.env.example`.

### Starting state

`docs/process/IMPLEMENTATION_PLAN.md` §8.3 and the 2026-08-29 journal both record that Vercel's
Git integration is already connected and has been posting successful pull-request previews for
weeks, while ENV-03 stayed open. So this was not "connect Vercel"; it was "make the deploy
contract a property of the repository and verify the parts the repository owns". Creating a
second project would have duplicated a working one — `docs/process/HUMAN_GATES.md` names that
explicitly as the thing not to do.

### What changed locally

- **`vercel.json`** (new). Build contract plus the SPA rewrite:
  - `installCommand: npm ci` and `buildCommand: npm run build` — the same lockfile-exact install
    and the same command CI runs, so a preview cannot resolve a dependency the PR did not pin.
  - `outputDirectory: dist`, `framework: vite`.
  - one rewrite, `/(.*)` → `/index.html`. Vercel serves a real file from `dist/` before it
    consults a rewrite, so hashed assets are unaffected and only unmatched paths fall through.
  - `github.enabled: true`, which is the setting that produces the per-PR preview and the
    production promote on `main`.
- **`.env.example`** (new). `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY`, names and
  placeholders only, with the Preview-scope warning and an explicit note that
  `SUPABASE_SERVICE_ROLE_KEY` and `ANTHROPIC_API_KEY` are not `VITE_` variables and do not
  belong in this file. `.gitignore` already carried `.env.*` plus `!.env.example`, so no change
  was needed there.
- **`src/test/deploy-config.test.ts`** (new, 15 tests). Asserts the build contract, that
  `outputDirectory` equals what `vite.config.ts` actually writes (it reads the config rather
  than restating `dist`), that the rewrite is a single catch-all to `/index.html`, and — by
  compiling the `source` pattern to a RegExp — that it matches `/`, `/history`,
  `/history/2026-09-21`, `/workout/<uuid>`, `/settings/locations` and a deeply nested path. It
  also holds the environment contract: every `VITE_` name app-owned source reads must appear in
  `.env.example`, no value may look real (a JWT-shaped string or a non-placeholder), and no
  `VITE_`-prefixed name may carry a server-side secret.
- **`DEVELOPMENT.md`**: new *Deployment* section — what triggers a deploy, why the rewrite
  exists (without it `/history` is a CDN 404 before any JavaScript runs, so the app's own 404
  screen never gets the chance to render either), and the environment-variable contract.
- **`README.md`**: a short *Deploys* section and a pointer to `.env.example`.
- **`PROJECT_MAP.md`**: rows for `vercel.json` and `.env.example` — a new deployment boundary,
  which is the bar the map sets for an entry.

Nothing changed in GitHub or in Vercel from this workspace. The execution contract for this task
forbids pushing, opening a PR, or merging.

## DATA-01a — Schema: catalog domain (issue #8)

Branch `agent-runner/task-009-a2-4459f172`. Second attempt; the first failed independent

### Intended outcome

Author the catalog-domain migration against the approved REQ-008 disposition and prove it with
`supabase db push --dry-run`, **without mutating the reused live project**. The off-machine-copy

### What changed locally

`supabase/` did not exist before this task; the repository had no migration series at all. Added:

  and no secret lives in the file. `major_version = 17` matches the live server's PostgreSQL 17.6
  from `docs/backend/capture/inventory-2026-09-18T162244Z.txt`. `[db.seed] enabled = false`
  because seeding is DATA-02's.
- `supabase/migrations/20260921000000_catalog_domain.sql` — five enums (`session_focus`,
  `movement_pattern`, `exercise_role`, `muscle_role`, `section_type`), five tables
  (`exercise_definitions`, `exercise_muscle_groups`, `exercise_pattern_weights`,
  `component_pattern_map`, `focus_pattern_map`), three views (`exercise_patterns`,
  `exercise_pattern_ranked`, `exercise_catalog`), RLS on every table, and the two taxonomy
  mapping seeds. `exercise_anchors`, `movement_patterns` and `anchor_type` are deliberately not
  created — they are being retired, and the only information they carried that derivation would
  lose (the primary/secondary ranking) has a home in `exercise_pattern_weights`.
- `supabase/migrations/00001…00029_*.sql` — twenty-nine no-op inherited history markers, plus
  `supabase/migrations/README.md` explaining them. Cause below.
- `src/test/catalog-migration.test.ts` — 22 tests over the migration artefact.
- `PROJECT_MAP.md` gains the `supabase/` boundary and the database flow; `.gitignore` gains the
  CLI's scratch directories.

**Nothing changed in GitHub or in Supabase.** The only network call made was the dry run, which
opens a read transaction against the live project's migration history and writes nothing.

### The failure that shaped the design

The first `supabase db push --dry-run` failed:

```
{"_tag":"Error","error":{"code":"LegacyDbPushMissingLocalError",
 "message":"Remote migration versions not found in local migrations directory.", …}}
```

The cause is not the migration. The rebuild reuses the live project, whose
`supabase_migrations.schema_migrations` already lists `00001`–`00029` from the previous
application — exactly the list the 2026-09-18 capture recorded. The CLI refuses to push while a
remote version has no local file, and its own suggested fix,
`supabase migration repair --status reverted 00001 … 00029`, deletes twenty-nine rows from the
live project. That is a row deletion, which `docs/backend/live-inventory.md` forbids until the
off-machine copy exists, and it is TASK-072's work besides.

So the local directory was made to match instead: one comment-only file per inherited version.
`supabase db reset` runs twenty-nine no-ops and then the real migration, producing a database
that is purely the new schema; `supabase db push` skips all twenty-nine because the live project
already has them. Nothing is faked and nothing is mutated. **This is a deviation worth naming:**
`docs/backend/dispositions.md` §9 dispositions the migration history as *Replace* — bookkeeping
resetting to the rebuild's own series. These markers are the pre-gate way to keep the CLI usable
without that reset, and `supabase/migrations/README.md` records that TASK-072 deletes every file
below `00030` in the same change that repairs the live history.

A second failure, self-inflicted: the retirement test asserted `exercise_anchors` appears nowhere
in the migration, and failed on the `COMMENT ON` that explains where `exercise_anchors` went.
Corrected by asking the question of the DDL with string literals blanked, which is the stronger
assertion anyway — a comment naming a retired table is documentation, a `CREATE TABLE` naming it
is a regression.

### What is proven, and what is not

The dry run proves the CLI accepts the migration set against the real project. The tests prove
the migration says what DATA-01a requires: RLS enabled on all five catalog tables, a
`FOR SELECT TO authenticated` policy on each, **no** insert/update/delete policy anywhere,
privileges revoked from `anon` and `authenticated` with only `SELECT` granted back, `service_role`
granted all, and `security_invoker = on` on the views so a view cannot read around those policies.

Neither executes SQL. **"Authenticated users can select catalog rows and cannot modify them" is
not yet proven behaviourally**, because proving it needs a database to prove it against and the
gate forbids touching this one. Docker and `supabase start` were both refused by the command
sandbox, so no local Postgres was available either. ENV-07 is where that check becomes
continuous; TASK-072 is where it first runs against the live project.
