## PWA-01 — Installable PWA (issue #64)

**Branch:** `agent-runner/task-064-a1-5a01b586` · **Intended outcome:** a manifest, a chamfered

### What changed locally

- **`public/`** (new directory, now in `PROJECT_MAP.md`): files a browser fetches by fixed URL.
  - `manifest.webmanifest` — `standalone`, `start_url` and `scope` `/`, `theme_color` and

- **`scripts/generate-pwa-icons.mjs`** (new) — renders the mark to PNG (192, 512, maskable 512,
  apple-touch 180) and exposes a Vite plugin that emits those files during `vite build` and
  serves the same bytes from memory in dev.
- **`index.html`** — manifest link, `theme-color`, SVG icon, `apple-touch-icon`,
  `apple-mobile-web-app-capable` / `mobile-web-app-capable`, app title, status-bar style.
- **`src/app/service-worker.ts`** + **`src/main.tsx`** — registration at `/sw.js` scope `/`, on
  `load`, `updateViaCache: 'none'`, off unless `import.meta.env.PROD`, failure swallowed.
- **`vercel.json`** — `Cache-Control: public, max-age=0, must-revalidate` on `/sw.js`.
- Tests: `src/test/service-worker.test.ts`, `src/test/pwa-manifest.test.ts`,
  `src/test/pwa-icons.test.ts`, `src/app/service-worker.test.ts`.

### Decisions, and why

**The icons are rendered by the build, not committed as binaries.** The export's
`assets/favicon.svg` sets a `C` in Oxanium and rounds its corners with `rx="6"`: a favicon loads
no webfont, and corner radius is 0 in this system. So the mark is drawn as geometry — orthogonal
and 45° edges only, per `assets/README.md` — with the `.clr-chamfer` bottom-right cut on the
badge and on both open tips of the `C`. The renderer is ~200 lines of scanline fill plus a
minimal PNG encoder over `node:zlib`; no image dependency was added.

**The renderer lives in `scripts/`, not `src/`.** It has to restate two hex values (`--base`,
`--structure`) because neither a PNG nor a manifest can read a CSS token. In `src/` that is a
DS-08 failure, and correctly so. `src/test/pwa-icons.test.ts` asserts both values still match
`src/styles/skin-clear.css`, so the restatement cannot drift silently.

**No stale-shell trap, at three layers:** the document is network-first with the cached shell as
the offline fallback only; the worker calls `skipWaiting()` on install and `clients.claim()` on
activate, and deletes every cache whose name is not the current version; and `/sw.js` is served
`max-age=0` so the update check itself is never answered from the HTTP cache.

**Nothing but the shell is cached.** Non-GET, cross-origin (Supabase, Anthropic), and same-origin
`/api/`, `/rest/v1/`, `/auth/v1/`, `/functions/v1/` requests are not handled at all — they fall
through to the browser's own network path, so there is no code path that could write them to a
cache. Fingerprinted `/assets/*` are cache-first because their URLs are immutable. This keeps
IA.md §5 true: data offline is still OFF-01 in M3.

### Failures and corrections

- The icon plugin first called `this.emitFile()` unconditionally, which Vite rejects in serve
  mode — every `vitest` run printed *"context method emitFile() is not supported in serve
  mode"*. Corrected with a `configResolved` flag: emit during `build`, serve via middleware
  otherwise.
- `src/test/pwa-icons.test.ts` asserted the SVG contains no `rx=`, and failed on the file's own
  header comment, which names the `rx="6"` it replaces. Corrected by stripping comments before
  asserting — the same distinction `src/styles/fonts.test.ts` draws between what a file requests
  and what it talks about.
- The worker is tested by evaluating `public/sw.js` against a fabricated worker scope rather than
  by grepping its source: a test that finds the word `skipWaiting` in a file proves nothing about
  a shell that loads offline. Requests are plain objects there because a real `Request` cannot be
  constructed with `mode: 'navigate'`.

### The failure that shaped the design

The first `supabase db push --dry-run` failed:

```
{"_tag":"Error","error":{"code":"LegacyDbPushMissingLocalError",
 "message":"Remote migration versions not found in local migrations directory.", …}}
```

The cause is not the migration. The rebuild reuses the live project, whose
`supabase_migrations.schema_migrations` already lists `00001`–`00029` from the previous
application — exactly the list the 2026-09-18 capture recorded. The CLI refuses to push while a
remote version has no local file, and its own suggested fix,
`supabase migration repair --status reverted 00001 … 00029`, deletes twenty-nine rows from the
live project. That is a row deletion, which `docs/backend/live-inventory.md` forbids until the
off-machine copy exists, and it is TASK-072's work besides.

So the local directory was made to match instead: one comment-only file per inherited version.
`supabase db reset` runs twenty-nine no-ops and then the real migration, producing a database
that is purely the new schema; `supabase db push` skips all twenty-nine because the live project
already has them. Nothing is faked and nothing is mutated. **This is a deviation worth naming:**
`docs/backend/dispositions.md` §9 dispositions the migration history as *Replace* — bookkeeping
resetting to the rebuild's own series. These markers are the pre-gate way to keep the CLI usable
without that reset, and `supabase/migrations/README.md` records that TASK-072 deletes every file
below `00030` in the same change that repairs the live history.

A second failure, self-inflicted: the retirement test asserted `exercise_anchors` appears nowhere
in the migration, and failed on the `COMMENT ON` that explains where `exercise_anchors` went.
Corrected by asking the question of the DDL with string literals blanked, which is the stronger
assertion anyway — a comment naming a retired table is documentation, a `CREATE TABLE` naming it
is a regression.

## ENV-05 — Supabase keep-alive (issue #5)

Branch `agent-runner/task-005-a2-ad9a7561`, second attempt. The first attempt left no commits and
no working-tree changes, so this session started from a clean tree at `627ae71` and implemented
the task from scratch; there was no partial work to correct.

### Intended outcome

A scheduled GitHub Action that keeps the free-plan Supabase project from pausing, pings it with a
harmless authenticated read, goes red visibly when it fails, and is documented as disposable.

### What changed locally

- `.github/workflows/keep-alive.yml` — new. Cron `23 6 * * 1,4` (Mon/Thu, 06:23 UTC) plus
  `workflow_dispatch`; `permissions: contents: read`; one `curl` GET carrying the anon key in
  headers read from the environment, body discarded, status code only; a second `if: always()`
  step that writes the request, status and a ranked diagnosis to the run summary and emits an
  `::error` annotation on failure.
- `src/test/keep-alive-workflow.test.ts` — new, 12 tests, written before the workflow was final
  and used as the feedback loop.
- `README.md` — new "Keeping Supabase awake" section: what the action does, the two secrets it
  needs, and the instruction to delete it and them on a paid plan.
- `PROJECT_MAP.md` — the `.github/workflows/` row said "pull-request automation", which this
  scheduled Supabase-touching job makes untrue.

Nothing changed in GitHub or any external service: no push, no PR, no workflow run, no secrets
created. The workflow has therefore never executed.

### The design decision worth recording

ENV-05 says "pings the database", and the obvious implementation is a `select … limit 1` against a
table. That implementation would be red from the moment DATA-01a is applied. Its grants are
`revoke all on <table> from anon, authenticated` followed by `grant select … to authenticated`
only, and every SELECT policy is `to authenticated` — so a browser-safe anon key has no readable
table in the rebuilt schema, and would get "permission denied" rather than a row. Naming a legacy
table instead (`exercise_definitions` exists in the reused project today) buys a green run now and
an unexplained red run at cutover.

The request is therefore an authenticated GET to the PostgREST root, `/rest/v1/`, held in a
workflow-level `env:` value so redirecting it at a readable endpoint later is a one-line change.
It requires the key (401 without one), reads nothing, and names no table the migrations are still
moving. **This is a deliberate weakening of the "pings the database" wording**: the root is served
from PostgREST's schema cache, so what it proves is that the project's API answers, not that a SQL
statement executed. Free-plan pause is driven by project API activity, so it is the right signal —
but if the intent was specifically a SQL round trip, the honest fix is a `keep_alive()` function
with `grant execute to anon`, which belongs to a DATA issue and cannot be applied while the
off-machine-dump gate in `docs/backend/live-inventory.md` holds. Flagging rather than widening.

The service-role key was considered and rejected: it would read any table, which is the opposite
of what a job that exists to read nothing should hold.

The tests prove the workflow says what ENV-05 requires: twice weekly with at most four days

**"Runs green on schedule and via manual dispatch" is not proven.** It cannot be from here: the
workflow has to exist on the default branch and the two secrets have to be set before a run is

so the two shell blocks were verified by review, not by execution — the reviewable risks are
`set -euo pipefail` with `"$(…)" || curl_exit=$?` (correct: `$?` on the right of `||` is the left
command's status) and the escaped backticks inside the summary's double-quoted `echo`s.
`git fetch origin main` was refused too; the branch was cut from `627ae71`, which is the newest
main this session can see, so no integration merge was possible or needed.
