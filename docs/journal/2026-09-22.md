### The design decision that took the most thought

The acceptance criterion is "a set log references the exercise row **actually performed**, and the
FK makes attaching it to a superseded prescription impossible". A plain
`REFERENCES workout_exercises (id)` cannot do that — it is defect D6 written as a foreign key, and
it accepts any row including one that was swapped out.

So the log references a **composite** key. `exercise_set_logs` carries
`prescription_revision_status revision_status NOT NULL DEFAULT 'active'` and
`FOREIGN KEY (workout_exercise_id, prescription_revision_status) REFERENCES workout_exercises
(id, revision_status)`, which needed a `UNIQUE (id, revision_status)` on `workout_exercises` to
point at. That constraint is added here rather than in DATA-01c because it exists only to serve
this foreign key; since `id` is already the primary key it forbids nothing that was previously
allowed.

Two things made that design non-obvious, and both are load-bearing:

1. **The column must not be client-settable**, or a caller could simply pass `'superseded'` and the
   foreign key would oblige. `exercise_set_logs` is therefore granted *column by column*, and the
   one column left out of both the INSERT and the UPDATE grant is
   `prescription_revision_status`. The requirement is expressed as a privilege, the same way
   DATA-01c expressed "never delete a prescription row" as the absence of a DELETE grant.

2. **`ON UPDATE CASCADE`, not the default.** My first instinct was to add
   `CHECK (prescription_revision_status = 'active')`, which would have been wrong: `DATA_MODEL.md`
   §7 requires that superseding an exercise the user already completed stays possible — "a
   superseded row still records that it was performed" — and a CHECK plus a cascade would have made
   the database refuse the swap. The cascade instead carries the stamp forward. The log stays
   attached to the row it was performed against; only its record of that prescription's current
   standing moves.

### Two deliberate deviations from the spec's illustrative DDL

Both are strictly stronger, both are driven by an acceptance bullet, and both are named in the
migration header rather than left for a reviewer to find by diffing:

- **`weight_unit` is NOT NULL.** `DATA_MODEL.md` §8 writes it nullable with
  `CHECK (weight IS NULL OR weight_unit IS NOT NULL)`; the requirement says the unit is on *every*
  set-log row, stamped at write time. NOT NULL says that and subsumes the CHECK. It also has no
  default, because a default here is exactly the profile-inheritance the column exists to prevent.
- **`id` has no `DEFAULT gen_random_uuid()`.** EXE-07 requires a client-generated id, "not a server
  sequence", so a retried flush is idempotent by construction. A server default would let a caller
  omit the id and silently lose that property on the retry that matters.
  `UNIQUE (workout_exercise_id, set_number)` is the second, independent guarantee.

### Where constraints were deliberately *not* added

`block_results` bounds its values and nothing else. The tempting constraints —
`completed_under_cap` requires `elapsed_seconds`, `partial_round_reps` requires
`rounds_completed` — would each contradict typed absence. "They beat the cap but the elapsed time
was never recorded" is a real state under I3, and a schema that refuses to store it is a schema
that has decided a null must mean something. A test asserts that no CHECK on that table names two
outcome columns, so the rule survives the next person who finds the same constraints tempting.

Similarly, `exercise_set_logs` carries no modality discriminator. Which actual columns *should* be
populated follows from `workout_exercises.modality`, one join away; a CHECK cannot read another
table, and a reps-prescribed set whose duration the user also recorded is a legitimate row.

### Failures and corrections

- **Two redundant indexes, caught on review.** `exercise_set_logs_exercise_idx` on
  `(workout_exercise_id, set_number)` duplicated the index `UNIQUE (workout_exercise_id,
  set_number)` already creates, and `block_results_block_idx` duplicated `UNIQUE (block_id)`. Both
  removed; the comments now say why no index is declared there.
- **A test that asserted too widely.** `expect(ddl).not.toMatch(/execution_status/i)` was meant to
  say "this table cannot store a skip" and instead failed the view, which legitimately *reads*
  `we.execution_status`. Scoped to the `exercise_set_logs` table body, which is the stronger
  assertion anyway — a column here could disagree with the exercise's status, a projection cannot.
- **Mutation-checked the new tests before trusting them.** Nullifying `weight_unit`, collapsing the
  composite foreign key to `(id)`, and restoring `DEFAULT gen_random_uuid()` on `id` each failed
  the suite (3 failures, all in the expected tests); the migration was then restored and
  reconfirmed green. The tests bite.

### What is proven, and what is not

The tests prove the migration says what DATA-01d requires it to say. **They do not execute SQL.**
The off-machine-backup gate forbids mutating the live project until TASK-072 and ENV-04 keeps
Docker out of the loop, so there is no database to round-trip against; `supabase db push --dry-run`
proves the CLI accepts the migration *set*, not that Postgres accepts each statement. The SQL was
reviewed by hand against the Postgres grammar. The behavioural proof — that the foreign key really
does refuse a superseded prescription, and that the column grant really does make the stamp
unreachable — is ENV-07's continuous job once there is a database to run it against.
