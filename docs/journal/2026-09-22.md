### The design decision that took the most thought

The acceptance criterion is "a set log references the exercise row **actually performed**, and the
FK makes attaching it to a superseded prescription impossible". A plain
`REFERENCES workout_exercises (id)` cannot do that — it is defect D6 written as a foreign key, and
it accepts any row including one that was swapped out.

So the log references a **composite** key. `exercise_set_logs` carries
`prescription_revision_status revision_status NOT NULL DEFAULT 'active'` and
`FOREIGN KEY (workout_exercise_id, prescription_revision_status) REFERENCES workout_exercises
(id, revision_status)`, which needed a `UNIQUE (id, revision_status)` on `workout_exercises` to
point at. That constraint is added here rather than in DATA-01c because it exists only to serve
this foreign key; since `id` is already the primary key it forbids nothing that was previously
allowed.

Two things made that design non-obvious, and both are load-bearing:

1. **The column must not be client-settable**, or a caller could simply pass `'superseded'` and the
   foreign key would oblige. `exercise_set_logs` is therefore granted *column by column*, and the
   one column left out of both the INSERT and the UPDATE grant is
   `prescription_revision_status`. The requirement is expressed as a privilege, the same way
   DATA-01c expressed "never delete a prescription row" as the absence of a DELETE grant.

2. **`ON UPDATE CASCADE`, not the default.** My first instinct was to add
   `CHECK (prescription_revision_status = 'active')`, which would have been wrong: `DATA_MODEL.md`
   §7 requires that superseding an exercise the user already completed stays possible — "a
   superseded row still records that it was performed" — and a CHECK plus a cascade would have made
   the database refuse the swap. The cascade instead carries the stamp forward. The log stays
   attached to the row it was performed against; only its record of that prescription's current
   standing moves.

### Two deliberate deviations from the spec's illustrative DDL

Both are strictly stronger, both are driven by an acceptance bullet, and both are named in the
migration header rather than left for a reviewer to find by diffing:

- **`weight_unit` is NOT NULL.** `DATA_MODEL.md` §8 writes it nullable with
  `CHECK (weight IS NULL OR weight_unit IS NOT NULL)`; the requirement says the unit is on *every*
  set-log row, stamped at write time. NOT NULL says that and subsumes the CHECK. It also has no
  default, because a default here is exactly the profile-inheritance the column exists to prevent.
- **`id` has no `DEFAULT gen_random_uuid()`.** EXE-07 requires a client-generated id, "not a server
  sequence", so a retried flush is idempotent by construction. A server default would let a caller
  omit the id and silently lose that property on the retry that matters.
  `UNIQUE (workout_exercise_id, set_number)` is the second, independent guarantee.

### Where constraints were deliberately *not* added

`block_results` bounds its values and nothing else. The tempting constraints —
`completed_under_cap` requires `elapsed_seconds`, `partial_round_reps` requires
`rounds_completed` — would each contradict typed absence. "They beat the cap but the elapsed time
was never recorded" is a real state under I3, and a schema that refuses to store it is a schema
that has decided a null must mean something. A test asserts that no CHECK on that table names two
outcome columns, so the rule survives the next person who finds the same constraints tempting.

Similarly, `exercise_set_logs` carries no modality discriminator. Which actual columns *should* be
populated follows from `workout_exercises.modality`, one join away; a CHECK cannot read another
table, and a reps-prescribed set whose duration the user also recorded is a legitimate row.

### Failures and corrections

- **Two redundant indexes, caught on review.** `exercise_set_logs_exercise_idx` on
  `(workout_exercise_id, set_number)` duplicated the index `UNIQUE (workout_exercise_id,
  set_number)` already creates, and `block_results_block_idx` duplicated `UNIQUE (block_id)`. Both
  removed; the comments now say why no index is declared there.
- **A test that asserted too widely.** `expect(ddl).not.toMatch(/execution_status/i)` was meant to

  `we.execution_status`. Scoped to the `exercise_set_logs` table body, which is the stronger

- **Mutation-checked the new tests before trusting them.** Nullifying `weight_unit`, collapsing the
  composite foreign key to `(id)`, and restoring `DEFAULT gen_random_uuid()` on `id` each failed
  the suite (3 failures, all in the expected tests); the migration was then restored and

## TASK-021 / AUTH-01 — Session context (issue #20)

**Branch:** `agent-runner/task-021-a1-cc80148d` · **Intended outcome:** the minimal session provider
over an auth client, exposing `{ status, user, signOut }`, that fetches nothing, guards nothing with
a ref, schedules nothing, and cannot present a failure as a signed-out user — half of defect D1.

### Starting state, and the decision it forced

The issue says "a minimal provider over `supabase.auth.onAuthStateChange`", but there is no
`supabase-js` in this repository and no `@tanstack/react-query` either. DATA-03 declined `supabase-js`
deliberately and on the record — its header says auth is AUTH-01's and that the PostgREST half is
`fetch` plus the generated types. Installing packages was not available in this workspace (network
commands were declined by the sandbox), so the choice was made on the merits and matches the
precedent: **AUTH-01 brings its own GoTrue session client** in `src/data/auth.ts`, shaped like the
part of `supabase.auth` the requirement names.

Two consequences, both recorded because a reviewer will ask:

- **`onAuthStateChange` carries a discriminated `AuthEvent`, not `(name, session | null)`.** The
  union has a member the Supabase shape has no room for — `RESTORE_FAILED` — and that member is the
  requirement. `SIGNED_OUT` and `RESTORE_FAILED` both leave the app with no user; only one of them
  is a decision, and D1 was the app being unable to tell them apart.
- **The React Query cache is a one-method port**, `QueryCache { clear(): void }`, injected into the
  provider. `QueryClient` satisfies it structurally, so AUTH-03 passes the real client without this
  file learning about the library. `signOut` clears it whether or not the revocation call succeeded,
  because the session is already gone locally by then.

### What changed locally

- **`src/data/auth.ts`** (new) — restore from storage, lazy refresh, `setSession` (AUTH-02's seam),
  `signOut`, and `sessionFromPayload` for AUTH-02's verify response. No timer anywhere: a token is
  exchanged only because a caller asked for one, which is also why the provider needs no guard
  against a refresh landing after unmount.
- **`src/state/auth-context.ts`** (new) — `status` / `user` / `error`, the pure reducer, `useAuth`.
- **`src/state/auth-provider.tsx`** (new) — subscribe, reduce, render.
- **`src/data/auth.test.ts`**, **`src/state/auth-provider.test.tsx`** (new) — 36 tests.
- **`PROJECT_MAP.md`**, **`src/data/README.md`**, **`src/state/README.md`** — the session flow.

**Nothing changed in GitHub, in Supabase, or in any other external service.** `gh issue view 20`
and every network command were declined by the sandbox, so the approved task body was used as the
implementation contract and cross-read against `docs/github/bodies/AUTH-01.md`, which carries the
same acceptance list.

### The two design points that took the thought

1. **Which refresh failures end a session.** Only GoTrue's own refusal — 400 or 401 on
   `token?grant_type=refresh_token` — clears the stored session. A rejected connection, a 500, a
   proxy's 502, a 429: the stored session stays exactly where it was and the subscriber is told
   `RESTORE_FAILED`, which the reducer turns into `status: 'error'` while keeping whatever user was
   known. This is the "failures never reset onboarding state" criterion, and it is enforced at both
   levels rather than trusted to the consumer.
2. **One in-flight refresh, in the client rather than in React.** GoTrue rotates refresh tokens, so
   two concurrent exchanges of the same token mean the second is refused and a live session is
   thrown away. The provider is banned from holding that guard and should be — there is one client
   and one token, so the client holds a single pending promise and every concurrent caller awaits
   it. A test proves two parallel `getSession()` calls make one HTTP call.

Related, and deliberate: the reducer hands back the **identical `user` object** across a token
refresh when the id is unchanged, so AUTH-03's queries keyed by `user.id` cannot be invalidated by a
refresh. That is the "no refetch storms" property bought at the only place it is cheap.

### Failures, and what they turned out to mean

- The seed parser first returned zero rows: the loop broke on the blank remainder of the
  `) values` line before reaching the first tuple. Fixed by skipping blank lines, and it now throws
  when a statement yields no rows, so a silent-empty fixture cannot come back.
- Two retrieval tests failed on first run and both were the library telling the truth, not the code
  being wrong:
  - a **bodyweight-only location cannot fill `primary_lift`** — every primary lift in the seeded
    catalog needs a barbell, dumbbell, kettlebell or bar. It is now an explicit test that the
    request fails with `GENERATION_NO_CANDIDATES` naming `primary_lift`, which is the requirement's
    "an empty set is a typed error rather than an empty workout".
  - filtering the catalog to mobility-tagged exercises empties three sections, not five: several of
    those rows are tagged `warmup`, `core` or `cooldown` too.
- `tsc` caught two things vitest did not: a duplicated `scope` key in a test factory, and a
  `Set<MovementPattern | null>` being asked about a `string`.

### Findings worth recording

- **`cooldown` holds six exercises in the whole seeded library**, so it is under §3's floor of 8 for
  every request and is always retrieved relaxed. That is the diagnostic working as designed — §12
  records 8 as a guess to be tuned against the real library — but it is a catalog thinness worth
  naming, and it is asserted rather than left to be noticed later.
- The seed tags no exercise for `skill_power`, `carries` or `stability_balance`. A profile that
  enables one of those would fail with `GENERATION_NO_CANDIDATES` for it. That is out of scope here
  and is not worked around; the default six sections are all populated.
