### Decisions worth recording

**The endpoint stays refusing.** GEN-02c owns validation against the candidate set (checks 1–3),
duration plausibility (check 8), hydration and persistence. Wiring the composer into the handler now
would mean either returning a workout nobody validated — an id or an equipment value outside the
candidate set reaching the client — or spending a model call and then refusing to answer with it.
Both are worse than the current typed refusal, so the composer is a tested module with no caller and
GEN-02c mounts it. The issue's own acceptance criteria are all properties of the prompt, the call
and the retry, and all are exercised.

**The system prompt is a copy of the spec, and the test is what makes that safe.**
`generation-prompt.test.ts` reads the fenced block out of `docs/specs/generation/PROMPT_v4.md` and
compares it byte for byte, so editing the prompt means editing the spec. The transcription was wrong
nowhere on the first run, but the test is the reason that is knowable.

**No candidate name reaches the prompt.** `PROMPT_v4.md` §1 lists what a candidate carries — ids,
patterns, roles, components, muscles, usable equipment, `can_be_primary` — and the name is not on it.
The old prompt spent its largest per-row cost on the display name of a thing the model is forbidden
to return, and hydration fills it in by id afterwards (§8).

**The clamp is applied to the request, not checked on the output.** The system prompt states
"Intensity is already clamped to 1–3" as an accomplished fact, so `resolveEffectiveRequest` is what
makes it one. Only `active_recovery` is clamped here: it is the only goal `PROMPT_v4.md` gives a
range to, and the per-goal slider cascade is GEN-04's. Inventing the other four ranges in this module
would put two answers in the codebase. The same function also fixes the announced sections to
warmup/mobility/cooldown for that goal, because `generation_candidates` overrides the profile's
toggles in SQL and a prompt describing a different section set would describe candidates the caller
never received.

**Upstream failures retry without an addendum.** §4's correction names what a prior *response* got
wrong. A network failure produced no response, so the retry re-sends the original prompt unchanged;
telling a model the network failed is an instruction it cannot act on.

### The §5 measurement

§5 asks for the `5.0.0` prompt to be compared with the captured baseline and says the result belongs
in this change rather than in the static spec. It is asserted in
`generation-prompt.test.ts > prompt 5.0.0 measured against the captured v4.0.0 baseline`, so it
cannot quietly stop being true. For the fixture request — strength, focus `lower_body`, intensity 8,
45 minutes, three sections, nine candidates:

| | prompt 5.0.0 | v4.0.0 baseline |
|---|---|---|
| System prompt | 5,589 B | 19,707 B |
| Candidate payload | 1,967 B (9 rows) | 2,535 B (9 rows + heading) |
| Output contract | 2,272 B | — (the old prompt had none) |
| Request, history, preferences | 593 B | not counted |
| **Total** | **10,421 B** | **≥ 22,242 B** |

53% smaller, and the baseline is a deliberate lower bound in two ways: the old function sent the
whole equipment- and anchor-filtered library, roughly a hundred rows where nine are rendered here,
and its own user context, request and history blocks are not counted at all. The system prompt alone
drops 72%, against the ~40% `GENERATION_CONTRACT.md` §2 predicted — the difference is the eligibility
rules that became `WHERE` clauses in GEN-02a. Row for row on the same nine exercises the saving is a
smaller 20%, which is the name, the sections list and the regression reference going away; scope is
where the rest of it comes from.

The baseline is read, not transcribed: `legacySystemPrompt` extracts the `SYSTEM_PROMPT` literal
from `docs/backend/evidence/previous-functions/generate-workout.prompt.ts`, and the library rows are
rendered in the old `buildUserPrompt` format from the catalog capture under
`docs/backend/snapshot/`. Both sides describe the same real exercises, so the difference is format
and scope and nothing else.

## GEN-06 — duration plausibility (REQ-038, issue #39)

Branch `agent-runner/task-038-a1-3c2fed70`, worked in an isolated worktree. Nothing was pushed, no
pull request was opened, and no external service was changed — no Claude call was made from this

### Intended outcome

Check 8 of GENERATION_CONTRACT §6, computed in code from blocks and prescriptions, closing D5: the
old check compared `estimated_duration_mins` — a number the prompt told Claude the answer to —
against the request that told it, and so could not fail.

### What changed

- `supabase/functions/_shared/duration.ts` (new) — §7's formula and nothing else.
  `WORK_PER_SET_SECONDS = 40`, `TRANSITION_SECONDS = 30`, `DURATION_TOLERANCE = 0.2` are the whole
  allowance model: no metadata table, no per-exercise override, no tempo parsing. `estimateBlock`
  branches once per structure — standard sums members and rests between a member's own sets;
  superset and circuit multiply members by the block's rounds and charge shared rest once per round;
  emom, amrap and for_time read the declared clock, `for_time` at the full cap. `estimateDuration`
  adds one transition per exercise inside a section and one per section, and rounds to the minutes
  `computed_duration_mins` stores. `checkDuration` is the verdict, with the detail a retry is told.
- `supabase/functions/_shared/validate.ts` — runs check 8 last, after checks 1–3, and returns
  `generation.duration_implausible` when it fails. `DURATION_CHECK` states the eighth row beside the
  seven in `HARD_CHECKS`; it stays out of that table because the table *is* the correspondence to a
  database constraint, and no constraint can refuse a workout for being too long. `QualityRecord`
  gains `computedDurationMins` beside `modelEstimateMins`, `Validated` gains the per-block
  breakdown, and the log line surfaces both numbers.
- `supabase/functions/_shared/claude.ts` — `GenerationFailure.DURATION_IMPLAUSIBLE`, and the
  correctable set now includes it, so the failure buys exactly one addendum-corrected retry through
  the counter every other hard check already uses.
- `src/test/generation-duration.test.ts` (new) — 27 tests.
- `PROJECT_MAP.md` — the `_shared/` paragraph now names the fourth module and what it refuses to do.

### Decisions worth recording

**The tolerance band is one-sided, and this is the decision that mattered.** §7 asks for a check
"within tolerance", which reads symmetric. It cannot be: a fixed 40s work-per-set knows nothing
about setup, cueing or a warmup single, so it under-counts real time by construction. Measured on
the canonical valid fixture — a 45-minute strength request — the computed duration is 28 minutes
while Claude's own estimate is 46. A symmetric ±20% band would therefore have rejected the
repository's one known-good workout, and every future good workout shaped like it. So the check
rejects overruns only, and the header of `duration.ts` says why: a shortfall is evidence about the
allowance, not about the workout, and §7's stated purpose is "reject workouts that clearly cannot
fit".

**A superset with no declared rounds.** `fixed_round_structures_have_rounds` constrains circuits
alone, so the schema legitimately admits a superset with `rounds: null` and §7's formula then has
nothing to multiply — a gap DATA-01c already recorded against the spec. Inventing a constraint here
would be this module deciding another requirement's shape, so `roundsOf` infers the count from the
members' own `sets`, floors it at one round, and sets `assumedRounds` so a counted block can be told
from an inferred one. The finding stands; it is not fixed here.

**Members of a round-based block cost one set per round.** The block is what repeats (§5), so
counting a member's own `sets` on top of the block's `rounds` would charge the same work twice.

**Rejected, never trimmed.** A test asserts the workout object is byte-identical after a failing
validation. Deciding what to cut is composition judgment and belongs to the model.

**The ratio observation was left alone.** `observeRatios` carries a note saying its honest
denominator is GEN-06's computed minutes. Re-denominating it changes what a soft metric means, which
belongs to the requirement that owns the metric, so only the stale "does not exist yet" wording was
corrected.
