### Decisions worth recording

**The endpoint stays refusing.** GEN-02c owns validation against the candidate set (checks 1–3),
duration plausibility (check 8), hydration and persistence. Wiring the composer into the handler now
would mean either returning a workout nobody validated — an id or an equipment value outside the
candidate set reaching the client — or spending a model call and then refusing to answer with it.
Both are worse than the current typed refusal, so the composer is a tested module with no caller and
GEN-02c mounts it. The issue's own acceptance criteria are all properties of the prompt, the call
and the retry, and all are exercised.

**The system prompt is a copy of the spec, and the test is what makes that safe.**
`generation-prompt.test.ts` reads the fenced block out of `docs/specs/generation/PROMPT_v4.md` and
compares it byte for byte, so editing the prompt means editing the spec. The transcription was wrong
nowhere on the first run, but the test is the reason that is knowable.

**No candidate name reaches the prompt.** `PROMPT_v4.md` §1 lists what a candidate carries — ids,
patterns, roles, components, muscles, usable equipment, `can_be_primary` — and the name is not on it.
The old prompt spent its largest per-row cost on the display name of a thing the model is forbidden
to return, and hydration fills it in by id afterwards (§8).

**The clamp is applied to the request, not checked on the output.** The system prompt states
"Intensity is already clamped to 1–3" as an accomplished fact, so `resolveEffectiveRequest` is what
makes it one. Only `active_recovery` is clamped here: it is the only goal `PROMPT_v4.md` gives a
range to, and the per-goal slider cascade is GEN-04's. Inventing the other four ranges in this module
would put two answers in the codebase. The same function also fixes the announced sections to
warmup/mobility/cooldown for that goal, because `generation_candidates` overrides the profile's
toggles in SQL and a prompt describing a different section set would describe candidates the caller
never received.

**Upstream failures retry without an addendum.** §4's correction names what a prior *response* got
wrong. A network failure produced no response, so the retry re-sends the original prompt unchanged;
telling a model the network failed is an instruction it cannot act on.

The baseline is read, not transcribed: `legacySystemPrompt` extracts the `SYSTEM_PROMPT` literal

### Intended outcome

workout — session, sections, blocks, exercises — in one transaction, stamped with

### Decisions worth recording

**The transaction was already written, and the honest contribution is one request.**
`persist_session` (SES-01a, `20260921000005_session_lifecycle.sql` §5) writes all four levels in one
plpgsql function, and `session-lifecycle-migration.test.ts` already asserts that clause by clause.
So this module does not reimplement atomicity; it makes exactly one PostgREST request, which is one
transaction, and the test asserts the request list is exactly that one call. Four inserts issued from
the edge function could not have been made atomic by any amount of care — which is why that function
exists — and writing a second client-side "transaction" would have been the wrong kind of thoroughness.

**No retry after a failed write, and that is a design decision rather than an omission.** A
generation retries once (`claude.ts`). A write cannot: the session id is minted by the database, so a
second attempt after an ambiguous failure cannot distinguish "not written" from "written and the
answer was lost", and in half those cases the user would end up holding one workout twice. Asserted:
a refused write leaves `calls()` at length one.

**The versions come off the workout, not off the constants.** `hydrate.ts` already carries
`promptVersion`/`contractVersion` for this reason; `acceptanceFor` reads them from there, so a
deployment that bumped the prompt between the model call and the write stamps the old number on the
old workout. Asserted with versions that are deliberately not this deployment's.

**Claude's estimate is in the payload and in no column.** `generationOutputSchema` requires
`estimated_duration_mins`, so the payload carries the number the model actually wrote — sending a
different one would be worse. What makes that safe is downstream: the test splits
`persist_session` out of the migration text and asserts the function body never mentions the field,
and asserts no duration column on the stored row holds the fixture's 46 (D5).

**A null focus is refused by the schema rather than by a branch.** `workout_sessions.session_focus`
is NOT NULL while `RequestedSession.focus` admits null — composing a session with no focus of the day
is legitimate, storing one is not. `parseBoundary` answers that with the path `session_focus` and
nothing reaches the database, which is one fewer hand-written rule to drift from the column.

**`adjustment_reason` is derived from the clamp the request already shows.** The column exists so "a
session that was clamped should say so rather than look like a request nobody made" (`prompt.ts`), and
the derived sentence quotes the request's own two numbers rather than restating a rule, so whichever
clamp moved the intensity it stays true. A caller can override it, including with `null`.

**The per-goal-preset runs read each arc out of the system prompt.** `GOAL SHAPES` in `SYSTEM_PROMPT`
states the section arc per goal, so the test parses it rather than restating five lists: a goal shape
edited in `prompt.ts` changes what those five runs are required to persist. Active recovery is
asserted twice — its arc, and the intensity clamp with the reason it records.

### Left out, and why

**The live run per goal preset is not done, and cannot be from here.** The criterion is "one live run
per goal preset persists a contract-valid workout honouring section scaling", and section scaling is
composition judgment the contract deliberately leaves in the prompt (§2) — so the criterion is a
statement about a real model call. It needs `ANTHROPIC_API_KEY`, which is not among this task's
execution prerequisites, and a live Supabase write, which the off-machine-backup gate in
`docs/backend/live-inventory.md` forbids until TASK-072. What is delivered instead is the
deterministic half of the same sentence: five pipeline runs, one per goal preset, from response text
through validation, hydration and persistence, asserting the persisted section arc against the goal
shape the prompt states, plus the versions and the goal snapshot on the row. That is not the live run
and is not claimed to be.

**The endpoint still refuses, typed.** `generate-workout/index.ts` is untouched. Wiring the handler
needs GEN-02a's candidate read from Deno, HIST-01's history, the profile's goal and enabled sections,
and GEN-06's computed minutes — and it needs a response shape that can carry a session id, which
`generationSuccessSchema` does not have. That is a contract change and another issue's call, not
something to make by the back door while adding a write path.
