### Intended outcome

  then exercise id), the active-recovery clamp, and §5's measurement.
- `supabase/functions/_shared/claude.ts` — the call, the fence-tolerant parse against CORE-03's

- `src/test/generation-prompt.test.ts`, `src/test/generation-compose.test.ts`, and two fixture
  modules — `generation-prompt-fixtures.ts` (candidates built from the read-only catalog capture)
  and `generation-response-fixtures.ts` (one valid response, three recorded invalid ones).
- `PROJECT_MAP.md` — the GEN-02b paragraph, beside GEN-01's.

Nothing in `src/` imports either new module, and `supabase/functions/generate-workout/index.ts` is
untouched: it still refuses, typed. That is deliberate and is the one scope decision worth

### Decisions worth recording

**The endpoint stays refusing.** GEN-02c owns validation against the candidate set (checks 1–3),
duration plausibility (check 8), hydration and persistence. Wiring the composer into the handler now
would mean either returning a workout nobody validated — an id or an equipment value outside the
candidate set reaching the client — or spending a model call and then refusing to answer with it.
Both are worse than the current typed refusal, so the composer is a tested module with no caller and
GEN-02c mounts it. The issue's own acceptance criteria are all properties of the prompt, the call
and the retry, and all are exercised.

**The system prompt is a copy of the spec, and the test is what makes that safe.**
`generation-prompt.test.ts` reads the fenced block out of `docs/specs/generation/PROMPT_v4.md` and
compares it byte for byte, so editing the prompt means editing the spec. The transcription was wrong
nowhere on the first run, but the test is the reason that is knowable.

**No candidate name reaches the prompt.** `PROMPT_v4.md` §1 lists what a candidate carries — ids,
patterns, roles, components, muscles, usable equipment, `can_be_primary` — and the name is not on it.
The old prompt spent its largest per-row cost on the display name of a thing the model is forbidden
to return, and hydration fills it in by id afterwards (§8).

**The clamp is applied to the request, not checked on the output.** The system prompt states
"Intensity is already clamped to 1–3" as an accomplished fact, so `resolveEffectiveRequest` is what
makes it one. Only `active_recovery` is clamped here: it is the only goal `PROMPT_v4.md` gives a
range to, and the per-goal slider cascade is GEN-04's. Inventing the other four ranges in this module
would put two answers in the codebase. The same function also fixes the announced sections to
warmup/mobility/cooldown for that goal, because `generation_candidates` overrides the profile's
toggles in SQL and a prompt describing a different section set would describe candidates the caller
never received.

**Upstream failures retry without an addendum.** §4's correction names what a prior *response* got
wrong. A network failure produced no response, so the retry re-sends the original prompt unchanged;
telling a model the network failed is an instruction it cannot act on.

### The §5 measurement

§5 asks for the `5.0.0` prompt to be compared with the captured baseline and says the result belongs
in this change rather than in the static spec. It is asserted in
`generation-prompt.test.ts > prompt 5.0.0 measured against the captured v4.0.0 baseline`, so it
cannot quietly stop being true. For the fixture request — strength, focus `lower_body`, intensity 8,
45 minutes, three sections, nine candidates:

| | prompt 5.0.0 | v4.0.0 baseline |
|---|---|---|
| System prompt | 5,589 B | 19,707 B |
| Candidate payload | 1,967 B (9 rows) | 2,535 B (9 rows + heading) |
| Output contract | 2,272 B | — (the old prompt had none) |
| Request, history, preferences | 593 B | not counted |
| **Total** | **10,421 B** | **≥ 22,242 B** |

53% smaller, and the baseline is a deliberate lower bound in two ways: the old function sent the
whole equipment- and anchor-filtered library, roughly a hundred rows where nine are rendered here,
and its own user context, request and history blocks are not counted at all. The system prompt alone
drops 72%, against the ~40% `GENERATION_CONTRACT.md` §2 predicted — the difference is the eligibility
rules that became `WHERE` clauses in GEN-02a. Row for row on the same nine exercises the saving is a
smaller 20%, which is the name, the sections list and the regression reference going away; scope is
where the rest of it comes from.

The baseline is read, not transcribed: `legacySystemPrompt` extracts the `SYSTEM_PROMPT` literal
from `docs/backend/evidence/previous-functions/generate-workout.prompt.ts`, and the library rows are
rendered in the old `buildUserPrompt` format from the catalog capture under
`docs/backend/snapshot/`. Both sides describe the same real exercises, so the difference is format
and scope and nothing else.

## GEN-02c, validation half — candidate boundary and the soft record (REQ-034, issue #35)

Branch `agent-runner/task-034-a1-0f87c3e9`, worked in an isolated worktree. Nothing was pushed, no
pull request was opened, no Supabase project or Claude API was called, and no external service was
changed. Every result below is local.

### Intended outcome

The approved task is the validation slice of GEN-02c: reject what the database would reject, prove
the correspondence rather than assert it, and record the soft observations without letting one of
them gate. Its three acceptance criteria are the issue's first three; hydration, the atomic
persistence transaction, `prompt_version`/`contract_version` stamping and the live run per goal
preset are the rest of GEN-02c and are **not** in this change — see "left out" below.

### What changed

- `supabase/functions/_shared/validate.ts` — new. `HARD_CHECKS` is GENERATION_CONTRACT §6's table as
  data: per check, the rule in §6's own words, whether it gates in the CORE-03 schema or here, the
  §9 code a failure carries, and the declaration in `20260921000002_workout_domain.sql` the database
  would refuse the row with. `checkReferences` runs checks 1–3 over every prescription;
  `observeQuality` computes the four soft observations; `validateComposition` does the first, returns
  on failure, and only then does the second.
- `supabase/functions/_shared/claude.ts` — `GenerationFailure.INVALID_REFERENCE` added so §9's
  vocabulary stays one list, `correctionFor` now corrects it, `ComposerConfig.validate` is an
  optional function, and the call/parse/validate sequence moved into one `attempt` helper so the
  three share one retry counter. `Composition.validation` is `null` when no validator was
  configured — nobody checked, not nothing wrong.
- `src/test/generation-validation.test.ts` — new, 38 tests.
- `PROJECT_MAP.md`, `supabase/functions/README.md` — the new module and the direction of its import.

### Decisions worth recording

- **The correspondence is falsifiable.** Every declaration in `HARD_CHECKS` is looked up in the
  migration's own table body, and every rule string is compared against §6's table parsed out of the
  markdown. Renaming `target_shape`, or adding a check with no constraint, fails a test.
- **Checks 4–7 are not re-implemented.** They are already `src/state/schemas.ts`'s discriminated
  target and its refinements, which ran in `parseCompletion` before validation was reached. The test
  proves each one gates by driving a violating payload through `generationOutputSchema` rather than
  by a second implementation that could drift from the first.
- **Check 8 is absent on purpose.** Duration plausibility is GEN-06's; `DURATION_CHECK_OWNER` says so
  and the spec-parity test asserts the eighth row exists in the contract and not in `HARD_CHECKS`. A
  listed check that enforces nothing is the defect the list exists to prevent.
- **Soft cannot gate, structurally.** `validateComposition` reaches its `ok` value before
  `observeQuality` is called. The test that matters is the one with a workout outside on all four
  observations still validating.
- **Ratios are measured as each section's share of prescribed exercises**, and the module says in
  its own comment that the honest denominator is GEN-06's computed duration. When that lands the
  observation gains a second metric and the record's shape does not change — which is why the record
  stores numbers rather than verdicts.
- **Validation reaches `claude.ts` as a function, never an import.** The retry budget is one counter
  for parse failures and reference failures together (§6 gives hard checks one retry between them),
  and `claude.ts` still knows nothing about candidates or quality.

### Failures and misleading signals

- The first run of the ratio test asserted `0.25`: the fixture workout has five prescribed exercises,
  not four. The assertion was wrong, not the code; it now also pins the denominator.
- One full-suite run failed in `src/ui/circuit-block.test.tsx:217` (`queryByRole('timer')` still
  present at a round boundary). It is a pre-existing timing flake in a file this change does not
  touch and does not import; the two runs either side of it passed. Recorded rather than fixed —
  fixing it is another issue's work — but worth an issue of its own.

### Left out, and why

The remaining GEN-02c acceptance criteria are untouched by this change and are stated plainly rather
than partially done: hydration of name, equipment display names, cues and regression by id;
persistence of sessions → sections → blocks → exercises in one transaction; `prompt_version` and
`contract_version` stamped on the session; and one live run per goal preset. The live run needs
`ANTHROPIC_API_KEY`, which is not among this task's execution prerequisites, and persistence needs a
write path that does not exist yet. `generate-workout/index.ts` therefore still refuses, typed —
which remains correct, because a validated workout that cannot be stored is not a workout the user
can be given.

### Unresolved and the next safe action

1. Where the `QualityRecord` is stored is still contract §12's open question — a column on the
   session or a table. This change returns it and logs it; it writes it nowhere.
2. The ratio denominator becomes GEN-06's computed minutes once GEN-06 exists.
3. `PREPARED_SECTIONS` — which sections a warmup is expected to have prepared for — is stated in
   `validate.ts` rather than in a spec. It is an observation threshold and gates nothing, but it is
   a judgment this repository has not written down anywhere else.
