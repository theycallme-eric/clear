## CORE-01 — Error taxonomy and request IDs

### Intended outcome

Create a typed error system that replaces stringly-typed errors. Every AppError carries a code,
an optional requestId, and a user-safe message. Document the conventions and enforce via review.

### Branch and issue

Branch `core-01-error-taxonomy` from synchronized `main`. Issue #15. Started in runway mode while
DS-01 (PR #76) awaits review — no dependency between them.

### Implementation

1. **Error codes**: Created `ErrorCode` enum with five categories: AUTH, NETWORK, VALIDATION,
   GENERATION, PERSISTENCE. Each category has 4 specific codes.

2. **AppError type**: Interface with `code`, `message`, `requestId?`, and `details?`. Created
   `createError()` factory function that auto-populates the user-safe message from the code.

3. **Request ID**: Format `req_<timestamp-base36>_<random-base36>`. Generator function returns
   unique IDs. Documented in both the source file and the conventions doc.

4. **Error messages**: 20 user-safe messages, one per error code. Factual and imperative, not
   apologetic. Never expose internal details.

5. **Result type**: Discriminated union `{ ok: true, value: T } | { ok: false, error: E }` with
   `ok()`, `err()`, `isOk()`, `isErr()`, `unwrap()`, `unwrapOr()` helpers.

6. **Type guards**: `isAppError()` and `toAppError()` for catching unknown errors at boundaries.

7. **Convention doc**: `docs/conventions/error-handling.md` with the rule, examples, requestId
   format, error categories, Result vs throw guidance, and review checklist.

## Full chronology — setup, GitHub migration, automation, and first Claude runway

### Why this consolidated record exists

Eric asked for a chronological record because the work had become difficult to follow and the
handoffs made progress appear more automatic than it was. The sections above are the checkpoint
notes written while the work happened. This section consolidates the complete sequence—including
false starts, misleading descriptions, user coordination, corrected readings, and unresolved
problems—so a later review does not have to reconstruct it from chat history.

This record uses Git commits, local reflog timestamps, GitHub issue and pull-request state, and live
CI results where those exist. Conversation events without a durable timestamp are kept in sequence
but are not assigned invented times. No token, login code, secret value, email content, or personal
data is recorded.

### 1. Orientation began in the wrong project context

- The stated goal was to understand how close CLEAR was to a PWA, then make the rebuild runnable by
  a coding agent for an extended period.
- The first repository exploration did not stay anchored to `clear-rebuild`; Eric had to stop the
  work and identify that folder explicitly because other `clear` folders were outdated.
- The immediate priority was corrected to: find the authoritative rebuild, determine what was
  genuinely local versus on GitHub, migrate the approved requirements into GitHub Issues, and use
  their dependency graph as the build queue. Workout-generation discussion was deliberately
  deferred until that footing was established.
- Process correction: future sessions must resolve and state the absolute repository path before
  reporting project status. Similar directory names are not evidence that they are interchangeable.

### 2. Local planning artifacts were initially mistaken for live GitHub state

- An early description implied that GitHub issues or a repository already existed. Eric challenged
  that claim directly.
- A real GitHub check showed that the target `theycallme-eric/clear` repository did not yet exist.
  Local issue numbers, generated issue bodies, and a DAG document were preparation artifacts, not
  proof of anything on GitHub.
- This was a trust failure, not just a terminology problem: the claim sounded like a completed
  external action without external evidence.
- Process correction: every external-state claim must be verified against the external service and
  reported as one of `local only`, `pushed`, `open on GitHub`, `merged`, or `deployed`. Generated
  scripts and local metadata must never be described as migrated until the live service confirms it.
