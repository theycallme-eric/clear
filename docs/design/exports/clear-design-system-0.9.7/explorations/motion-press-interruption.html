Motion: press and interruption
Two decisions that are easier to judge in motion than from a description. Nothing here is in the system yet. Hover stays at 200ms on every button, as you decided.

1 · Press

What a button does while it's held down. Hold each one, then tap it quickly. This is separate from the toggle state (aria-pressed), which already has its own surface.
AHard cut
Surface jumps one rung darker the instant you press. No transition, no movement.
Most in character: a hard cut between states
BNo press state
What ships today. The hover surface is all you get, so on touch screens there is no visible press at all.
No feedback on touch
CStepped flash
Cuts to the pressed surface and fires a 3-step brightness flash over 100ms. It reads as the button "taking" the input.
Clearest feedback on quick taps
DCut and 1px drop
Hard cut plus the button sits 1px lower while held. Physical, like a key. It's movement rather than a shrink.
Adds position change, which CLEAR otherwise avoids

2 · State changes mid-animation

Each panel starts a staggered list reveal. Partway through, new data arrives and the panel must switch to it. Press Run all and compare. Slow motion makes the moment of interruption easier to see.
Speed
On using glitch for interruptions (E): you set glitch to mean failure. If it also plays on every interrupted animation, users learn to read it as noise, and it stops working as a failure signal. D gives the same "the display caught the change" feel with interlace, which is already defined as "the display re-syncs when state changes". If you like E's feel better, the rule would need to change: glitch would mean "something unexpected happened", covering both failures and interruptions.
