## IA questions answered

All five, and two changed requirements rather than just documentation.

**"Workout is a focus mode"** is the one with teeth. No in-app navigation out of an active session
— and the reasoning Eric gave is better than the one I'd have written: every route reachable
mid-workout is a chance to strand a session in an ambiguous state, so removing the exits removes
the whole class of bug. Focus is the felt benefit; state safety is the engineering one.

The distinction worth preserving: **the trap is on navigation, not on the user.** Closing the tab or
backgrounding the phone still persists and resumes. Trapping the person would be hostile; trapping
the router is just correct.

**Repeated favorites** stay separate sessions with a comparison card threading them. Landed on
FAV-02, which already owned personal bests and completion history.

## One thing his phrasing surfaced

He said "regenerated" where I'd asked about "restarted," and the slip is interesting. Regenerating
from Review discards a workout silently — no trace. But *"regenerated three times before starting"*
is the app being told, precisely, that generation failed to produce something worth doing. It's the
only honest signal of generation quality obtainable without asking the user a question.

Nothing records it. Flagged for the schema pass: capture it, or decide deliberately not to. Cheap
now, invisible later.

## D6 — swapped exercises are never persisted

Traced while writing the v0.4 change set, and it is worse than a design gap.

Generation saves the original prescription. `useExerciseSwap` mutates React state only — no write.
`handleStartWorkout` records a timestamp and navigates — no write. The only post-save writes to
`exercises` are `weight_logged` and `exercise_notes` at completion.

So: swap Deadlift for Romanian Deadlift, log 3×8 at 185, and the database records **3×8 at 185 on
Deadlift**. Set logs attach by `exercise_row_id` to rows describing exercises the user never did.

Silent corruption of the exact table progressive overload reads. OVR-01's load anchors would compute
deadlift capacity from RDL sets and never know they were wrong.

This moves the prescribed/revised/performed model from architectural preference to **correctness
requirement**, and it gives SES-01 a regression test with a specific reproduction rather than a
principle.

## §8 revised — metadata derives rather than gets authored

The earlier version proposed five attributes and an authoring workstream across 173 movements.
Traced back to the defect it was meant to serve, duration needs exactly two numbers per exercise:
seconds per rep, and transition time. Both derive from columns that already exist — `exercise_role`
and `default_equipment`. Modality isn't a per-exercise property at all; it belongs to the
prescription, where §5 already puts it.

Net new authoring: zero. Two lookup tables of ~7 and ~6 entries.

The method is the point: **evidence first, exceptions second.** Ship the engine with defaults,
compare computed duration against `duration_mins` which is already recorded, fix what's actually
wrong. Pre-classifying 173 movements to avoid a problem that may affect four of them is the
expensive version of the same outcome.

`impact_category` and `technical_demand` deferred with written revival conditions. Both existed for
a safety layer needing fitness-domain review; deferring them removes that dependency rather than
working around it. The safety mechanism is user-authored exclusions, where the user is the authority
on their own body.

**Cost of the detour:** three positions in three turns — authoring workstream, research session,
neither. The endpoint is right but the churn was real, and the check that would have prevented it is
cheap: before proposing new data, ask what existing columns already answer the question.

## v0.4 revision 3 — third-party pass, and two inconsistencies I missed

The reviewer caught the same error twice in my document: §7 promised deterministic technical-tier
and impact ceilings while §8 deferred the catalog metadata needed to enforce them, and §9 offered an
impact constraint against that same deferred data. **A rule that cannot be enforced is not a rule.**
Both are now removed rather than papered over.

Their I3 revision is better than mine. I had a reason code beside every optional field; they replaced
it with a status on the execution item (`not_started` / `completed` / `skipped`) plus plain nullable
values, with modality determining not-applicable. Same guarantees, far less ceremony. A skipped
exercise is a status, not three annotated nulls.

Their I1 revision is the same kind of correction: I was specifying versioning *architecture* inside
an invariant. It now states the outcome — originally generated prescription reconstructable,
lineage retained — and lets the schema pick the mechanism.

Duration went from an engine to a guardrail. Fixed 30–45s per set, `(sets − 1) × rest`, shared rest
once per round, For Time budgets the full cap, ~15–20% tolerance. Allowances live as code constants.
`DATA-04` withdrawn entirely.

The framing that survived and matters: **D5 is a tautology, not a precision problem.** The prompt
tells Claude the duration, Claude repeats it, the validator confirms it matches. The check cannot
fail. Any independent computation is strictly better, which is why crude is fine.

Also corrected: §13 previously claimed the change set satisfied the acceptance checks. It contains
no schema, so it cannot. Reframed as obligations the forthcoming schema must demonstrate.

Two pieces of context they lacked, neither changing a directive: `workout_sections` already carries
`started_at` / `completed_at`, so a persistent overrun can be traced to a section (not an exercise);
and `prompt_version` already exists on sessions, so version stamping is an extension rather than
new ground.

**Net across three revisions:** five new requirements → two. The parts that survived every pass are
the ones tied to verified defects.

## Schema written — and the taxonomy split cost nothing

The best finding of the whole pass: **the movement-pattern layer already exists.**
`exercise_definitions.component_movements` is populated across 142 exercises with 20 values, and it
is *more* precise than the anchor enum — it distinguishes `vertical-press` from `horizontal-press`,
`vertical-pull` from `horizontal-pull`, where the flat anchors just say "press" and "pull."

So the split requires **zero re-tagging**. Patterns derive from a nine-row mapping table
(component → pattern) and a four-row one (focus → patterns). Correct a mapping and every exercise
updates at once.

`power` resolves cleanly too — it maps to `triple-extension`, a real movement primitive shared by
power cleans, hang cleans, and push presses. It stops being a special case bolted onto a pattern
enum, which is what it is today.

`exercise_anchors` gets dropped entirely: its pattern data is redundant, and its region tags
(`full_body`×3, `upper_body`, `lower_body`) were exactly the conflation being removed.

Fourteen cascade points documented. The one that matters most: *"Upper Body → Press OR Pull"* stops
being a paragraph of English in the prompt and becomes a query.

## Lineage: append and supersede

I1 asked for reconstructability and lineage, not versioning architecture. The mechanism that falls
out is small — a swap inserts a new `workout_exercises` row with `replaces_id` pointing back, marks
the old one `status='replaced'`, and set logs attach to the new row.

That single arrow is D6. The three states become filters rather than tables:
`origin='generated'` · `status<>'replaced'` · join the logs.

Whole-workout versioning would have duplicated every unchanged row on every swap and turned "what
did I actually do" into a reconciliation problem.

## Two details worth keeping

`reps_prescribed` is **snapshotted at log time**, not joined — so revising a prescription later
cannot retroactively change what a completed set was measured against.

`weight_unit` is **per set-log row**, not inherited from the profile. A default that changes must
never silently reinterpret history. That is an injury path, not a display bug.

## Generation contract v4.1

The pipeline is now: resolve → retrieve → **compose** → validate → hydrate → persist. Claude occupies
exactly one step, the one requiring judgment. Everything on either side is deterministic.

The reduction is the point. Rules currently described to the model in prose become constraints
applied to its input:

- Exercise Inclusion Rule → the eligibility WHERE clause
- "Upper Body → Press OR Pull" → a focus_pattern_map join
- Equipment and enabled sections → the query
- "You MUST only use IDs from this list" → structurally true; Claude only sees eligible IDs
- Full library dump (~140 exercises) → ~40 candidates per request, fewer fields each

System prompt drops ~40%, candidate payload ~70%. Fewer input tokens, fewer output tokens, and
fewer retries — the retry being the largest latency cost, since it runs everything twice.

**The validation split matters more than the reduction.** Hard checks (8) are deterministic and
mirror the schema's CHECK constraints, so a workout that validates is one that can be persisted.
Soft checks (ratios, warmup coverage, variety, repetition) are recorded and never gate. A soft rule
that rejects is a hard rule with a soft name.

`usable_equipment` is computed per candidate, so Claude only ever sees equipment it may choose.

Kept Claude's `estimated_duration_mins` as **diagnostic only** — comparing its estimate against the
computed one is a free signal about whether the model understands the time cost of what it composed.
Never authoritative.

## Specs revision 2 — the blocks table was the real fix

Third-party review of the schema. Seven of eight points taken; one partially.

**Blocks were a genuine normalization error on my part.** `structure_type`, `timer_type`,
`timer_seconds`, `round_rest_seconds` sat on every member exercise — duplicated per member, with
nothing stopping three exercises in one circuit from disagreeing about the clock.

The sharper half: `structure_results` was keyed to `section_id`, so a conditioning section holding
an EMOM *and* an AMRAP could only record one. I inherited that from the existing schema without
questioning it — which is exactly what a rebuild is supposed to catch.

One table fixed three things: rounds now belong to the block (killing `modality: rounds`), block
results have a correct home, and shared rest is counted once per round instead of once per member.

**`{8,10}` was ambiguous** — a rep range or two ladder rungs, indistinguishable in an int array.
Now `target_kind` (fixed / range / sequence) plus `per_side` and `distance_unit`.

**Lineage needed to be temporal.** `revision_status = 'active'` gives the *currently* active
prescription, not what was active at `started_at`. Those diverge the moment a swap happens
mid-workout — and after-start regeneration is still an open policy question, so the schema must not
assume the answer. Now `created_at` / `superseded_at` / `slot_id`.

Also split `status` into `revision_status` and `execution_status`. Collapsing them meant replacing a
completed exercise overwrote `completed` with `replaced` — losing the fact it was performed.

### Where my context overruled the reviewer

- **`perceived_effort` stays.** They said only add it if the UI collects it. `EXE-04` already
  specifies section RPE capture, so the collection point exists in the spec.
- **Equipment filtering was already correct** — in `GENERATION_CONTRACT.md` §3, `usable_equipment`
  is computed per candidate. The data model's illustrative query was looser. A doc inconsistency,
  not a design flaw.
- **`avoid` / `prefer_not` stay modelled**, but the UI exposes `exclude` only until a ranking layer
  consumes them. Removing them from the model would be the wrong fix for a real concern.

### Where they were most right

The taxonomy. `exercise_anchors.is_primary` carries authored ranking my derivation discarded —
push-press has both `vertical-press` and `triple-extension`, so pure derivation makes it equally a
press and a power movement.

Resolved not by running two systems in parallel but by making the anchor data a **weighting layer
over derived patterns**: components produce candidates, `is_primary` ranks them. Coverage can be
partial without breaking anything.

And they were right that the fourteen-item taxonomy cascade is unrelated to D5/D6. It is now its own
staged migration with an equivalence check in `DATA-02`'s acceptance, not slipped in as part of a
defect fix.

### Caught by neither review

`saved_workouts.workout_snapshot` is JSONB in the shape of its era. Structured prescriptions change
that shape, so every existing favorite becomes unrestorable and future ones break on the next
contract change. Now carries `snapshot_contract_version`, validated before restore.

## Requirements v0.4 — everything folded

53 requirements, 257 acceptance criteria, graph re-verified. Every spec path referenced by the
requirements resolves to a real file in this workspace.

Three additions to make the document usable months from now rather than just complete:

**A glossary.** v0.4 introduced precise meanings for *prescribed*, *revised*, *performed*, *block*,
*slot*, *session focus*, *movement pattern*, *modality*, *target*, *candidate set*, *hard check*,
*soft check*, *typed absence*. Those distinctions are load-bearing — conflating revised and
performed is how a system convinces itself you are progressing when you are deviating — and none of
them are obvious from the requirement text alone.

**A specification index.** Requirements state what and how it is verified; specs carry the detail.
The index maps each spec to the requirements it serves, so a build agent picking up EXE-04 knows to
read the ladder spec and the data model without hunting.

**Version history in the header.** Five versions with what changed and why, including which
requirements were proposed and withdrawn — which is why there is a gap between DATA-03 and DATA-05.

Also swept for stale references: `structure_results`, `suggest_anchor`, "prompt v3", "200+
exercises", "duration ±10%", "the old schema's end state". All gone.

The requirements now describe the rebuild as designed rather than as first imagined, and every claim
in them traces to either a verified defect or an approved decision.

## Third review pass — and a better sizing rule

Outside review of the requirements. All eight claimed contradictions verified against line numbers;
every one real. Five were mechanical and are fixed. Three were product decisions and went to Eric.

**The sizing critique was the important one, and the fix was to delete the claim rather than improve
it.** "~1–3 hours per requirement" was never true — DATA-01 alone is the whole baseline schema. But
re-estimating is the wrong repair. The criterion should be *independently mergeable and
independently verifiable*; elapsed time on agent work is noise.

The reason it matters is sharper than "tickets are big": an oversized node causes **false
serialization**. GEN-06 needs GEN-02's validation, not its hydration or persistence — so a coarse
GEN-02 makes GEN-06 wait for work it does not depend on. The graph lies about the plan, which is the
one thing a DAG must never do.

**Spec coverage was 24/53.** The issue generator copies each requirement's own `Spec:` field, so the
specification index — "every UI requirement uses IA" — reached exactly nothing. Nine UI requirements
cited no spec at all. Now 53/53, with self-contained ones saying so explicitly rather than leaving
the field blank, so a generated issue never looks like it lost a reference.

## The decisions, and what they have in common

All three were the same question wearing different clothes: **is M1 the version that works for Eric,
or the first version someone else could touch?** He chose the former, consistently.

Onboarding stays M2 with a placeholder. Streak gets a minimal derivation in M1 that HOME-02 extends

That last one is the principle stated plainly: *nothing on the screen is non-functional.* It is the
same rule that killed the mock-workout fallback — an app that shows you something that does not work
is lying, whether the lie is a fake workout or a dead button.

## The stubs would have been stranded

Eric asked whether progressive overload was the only M3 feature — he remembered eight or nine
candidates. It surfaced a real gap: the issue script created 53 requirements and **none of the 8
stubs**.

That matters because of the source-of-truth handoff already written into the traceability section:
this document governs until issues are created, and from that moment GitHub is live truth. Under
that rule, eight future features — 1RM mode, mid-workout swap, inline editing, progression charts,
offline, cues enrichment, retention, Capacitor — would have existed only in a markdown section
nobody opens.

Now 61 issues: 53 buildable plus 8 labeled `needs-spec`, carrying no acceptance criteria and an
explicit *do not start this issue — close it into requirements, don't implement it.*

The instinct worth keeping: **anything real belongs where the work is tracked.** A backlog that
lives somewhere else is a backlog that quietly becomes a list of things you meant to do.
